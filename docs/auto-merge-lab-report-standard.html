01 / ARCHITECTURE

Authority stays outside the model.

The model answers a narrow semantic question. Trusted code gathers evidence, decides whether the model may run, rechecks every mutable fact, and performs the exact-head merge.

Exact binding

Approval belongs to one repository, PR, head SHA, base ref, live base SHA, and policy fingerprint, with a separate context fingerprint proving the evaluated evidence.

Advisory intelligence

The model assesses intent, coherence, and unusual risk. It never supplies authoritative forge facts.

Fresh authorization

Trusted postflight repeats every mutable gate immediately before mutation and rejects drift.

authority tuple: (repository, pull_request_number, head_sha, base_ref,
live_base_sha, policy_fingerprint) · evidence: context_fingerprint
02 / WHAT WE DID

We exercised the whole system.

This was not a mocked merge call. The normal Fullsend roles created, reviewed, fixed, tested, and ultimately merged a real pull request in the isolated lab.

ISOLATE

Created one private repository and repo-scoped identity

Fullsend was installed per-repository. A dedicated workload-identity provider trusted only ascerra/auto-merge. The public mint and its resources were untouched.

ISSUE

Triggered the normal triage path

Issue #1 received /fs-triage, proving the standard event router and triage agent worked in the new repository.

CODE

Had the code agent open PR #2

The change was deliberately small: one documentation behavior update constrained by repository instructions and an allow-listed path.

REVIEW + FIX

Ran the review/fix loop

Review requested a semantic correction. Fix updated the change. This exposed that generated per-repo configuration omitted the fix role, so it was enabled explicitly.

CI

Waited for both exact-head checks

The fast contract check passed, followed by a deliberate four-minute integration check. Approval and checks were verified against the final signed-off head.

SAFE FAILURE

Observed a correct escalation

The first Auto-Merge run lacked the PR patch in model evidence. The model returned ESCALATE; receipts were written and no merge occurred.

HARDEN

Added bounded patch and live-base binding

Preflight now requires bounded API patch evidence and proves the synthetic merge preview has ordered parents [live base, exact head].

MERGE

Merged the exact approved head

The final model result was APPROVE. Trusted postflight revalidated the tuple and squash-merged head 3b1a3ac as bfad1a0.

04 / FORGE BUTTON ALONE

“Merge when ready” is not a complete authorization system.

Native forge auto-merge is valuable, but the button delegates a future merge to whatever repository rules happen to be configured. That is narrower than the Auto-Merge contract we proved.

What GitHub does well

GitHub waits for configured required reviews and status checks. Its merge queue can also test a queued change against the latest target branch and earlier queued pull requests.

The boundary

The forge can enforce configured mechanical rules; it does not, by itself, prove that this exact patch still matches the issue, fits the low-risk cohort, carries a bound semantic decision, or has our required audit receipts.

1. It is standing future authorization.

The button is pressed before readiness is complete, and the forge merges later when its requirements become true. GitHub documents automatic disablement when a contributor without write permission pushes or the base branch changes; that is not the same guarantee as revoking intent on every revision change.

2. It checks only configured rules.

A missing, renamed, duplicated, incorrectly sourced, or non-required check is outside the button’s safety story. The button cannot know the organization intended a stronger policy than the repository currently expresses.

3. Exact-head review freshness is optional.

Dismissal of stale approvals and approval of the most recent reviewable push are separate branch-protection settings. Without them, “an approval exists” is weaker than “approval applies to this exact head SHA.”

4. Latest-base testing is optional.

Testing against current main requires an up-to-date-branch rule or a merge queue. A normal green PR check can describe an older base relationship unless repository policy closes that gap.

5. There is no semantic fit decision.

Required checks can validate code, but the native button does not judge whether the patch matches the issue, remains routine and bounded, introduces hidden coupling, or deserves human escalation.

6. It lacks our authority receipts.

The forge records ordinary audit events, but not our immutable evidence hash, semantic reasons, pre-mutation decision receipt, postflight comparison, and explicit stale-decision outcome.

7. Bypass configuration can weaken guarantees.

Branch protection and rulesets may allow privileged actors to bypass requirements unless “do not allow bypassing” and related controls are intentionally configured.

8. It cannot reconcile our ambiguous outcome.

If an external controller loses the forge response, it still needs an idempotent receipt and a fresh state lookup before retrying. Clicking the button does not supply that controller protocol.

Recommended role for the forge

Use GitHub’s exact-head merge API or merge queue as the final execution mechanism behind the Fullsend authority boundary. Keep semantic assessment, exact tuple binding, write-ahead receipt, and immediate postflight revalidation in the trusted Auto-Merge controller. Native auto-merge alone should not be a second enablement path.

Current behavior references: GitHub auto-merge, protected branches, and merge queues.

05 / RECEIPTS

Two events, two different proofs.

The apparent duplication is intentional at the data-model level: authorization must be durable before mutation, while the eventual outcome is not known until afterward.

Before mutation

Decision receipt

Records the semantic decision, exact binding, deterministic findings, evidence hash, workflow identity, and timestamp.

→
After attempt

Outcome receipt

Records whether the PR merged, was rejected as stale, or remained unmerged after a non-approve decision.

Recommended refinement: keep both append-only events, but make the second receipt reference the first receipt or evidence hash and include only the outcome, merge SHA, and timestamp.
06 / LESSONS

The lab found real integration gaps.

Patch evidence must be explicit.

A trusted base checkout is not enough for semantic review. API-sourced bounded patches now form part of the evidence contract.

PR base metadata can lag reality.

Eligibility now compares the live branch SHA and the merge-preview parent tuple, rather than trusting only pull_request.base.sha.

DCO policies must align.

Hosted code/fix behavior omitted or declined sign-off, forcing a manual signed history repair before the lab could proceed.

Fix needs intentional configuration.

The generated per-repo role list did not include fix, even though a review/fix loop was part of the requested workflow.

One merge mechanism is safer.

The legacy CODE_AUTO_MERGE path is deliberately excluded. The custom agent is the single Auto-Merge enablement path.

Comments are enough for a lab.

Production needs idempotent receipt storage and explicit reconciliation after ambiguous forge timeouts.

Aggregate mergeability can self-deadlock.

GitHub reports unstable while Auto-Merge's own check is pending. Explicit exact-head checks must be authoritative; conflict, behind, blocked, and unknown states still fail closed.

A readiness label is not always a wake-up event.

A label written with GITHUB_TOKEN does not recursively start another workflow. The approval event completed this run; production needs trusted dispatch or reconciliation for the opposite event ordering.

08 / PRODUCTION GAPS

Successful lab, not production completion.

These are the remaining boundaries to solve before treating this as a production Auto-Merge capability.

  1. Provide a purpose-built, least-privilege merge identity instead of reusing the hosted coder identity.
  2. Align Fullsend-generated per-repo roles with the requested review/fix loop.
  3. Align autonomous commit behavior with DCO requirements so history repair is unnecessary.
  4. Use branch protection or rulesets in production; the private personal lab could not enable them.
  5. Add a per-PR lease or merge-queue authority to serialize final live-base validation with the forge request.
  6. Store receipts idempotently and reconcile forge state before retrying ambiguous mutation outcomes.
  7. Add trusted dispatch or periodic reconciliation so CI completion can wake Auto-Merge even when a workflow-token label cannot recursively trigger Fullsend.
  8. Load trusted current base-branch configuration for lifecycle events without weakening the untrusted-head checkout boundary.
