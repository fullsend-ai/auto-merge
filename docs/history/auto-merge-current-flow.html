Auto-Merge: the current flow

A simple map of what happens before the model runs, what the model is allowed to decide, and what the trusted runtime rechecks before asking GitHub to merge. Click any box to open the exact implementation or hosted evidence.

Current implementation: fc04011 on main. Smoke test: PR #11.

1 · Trusted Fullsend pre-script — before the model is called

TriggerWake upAutomatic handoff on a trusted Review Agent approval; authorized human comment/manual request remains available. D1 · collectRead live SCM factsFetch the pull request, base branch, reviews, comments, risk assessment, and optional quality evidence into secret-free evidence. D2 · gateCheck prerequisitesOpen, non-draft, exact repository/base, same-repository head, current Review approval, current risk, bounded human context, and allowed risk. Fail closedStop before modelIf prerequisites are missing or stale, record the reason and do not spend a semantic-agent run.

Important boundary: these checks do not decide whether GitHub’s required CI, review count, conversation resolution, branch freshness, mergeability, or queue policy passes. GitHub remains the authority for those mechanical facts.

2 · Fullsend agent runtime — inside the OpenShell sandbox

N1 · inputRead bound evidenceThe agent sees the exact revision, Review attestation, risk rationale, human signals, optional quality evidence, and repository instructions. N2 · judgmentMake semantic decisionAssess intended outcome, risk, coordination, follow-up, and unresolved human “hold / do not merge” context. N3 · outputReturn JSON onlyAUTHORIZE, DEFER, or ESCALATE with reasons, blockers, comment IDs, and an unchanged binding. Sandbox boundaryNo merge authorityThe model has read/write-to-output tools only; GitHub credentials and merge authority stay outside the sandbox.

3 · Trusted Fullsend post-script — after the model responds

D3 · validateValidate resultRequire a valid decision, exact binding, bounded reasons/blockers, and ready prerequisites. AUTHORIZE cannot contain blockers. D4 · postflightCollect fresh evidenceRe-fetch semantic state, verify fingerprints and policy, and stop if the head, base, policy, or context changed. D5 · modeObserve or authorizeObserve mode records the decision without mutation. Automatic mode writes a pending receipt, performs one final fresh check, then proceeds. A · SCM requestAsk GitHub to mergeUse native gh pr merge --auto --squash --match-head-commit; never bypass GitHub’s configured path.

DEFER / ESCALATE

Write or print a receipt, make no merge request, and leave the PR for human attention or a later context change.

AUTHORIZE

After fresh validation, submit the exact head to GitHub’s native direct or queue path. The agent is done at this handoff.

4 · GitHub / SCM — final mechanical authority

SCM · checksRequired CI and checksGitHub decides whether repository-configured status checks pass. The demo includes a quick check and a four-minute illustrative check. SCM · queueDirect or queue pathIf the repository requires a merge queue, GitHub queues the exact requested head; otherwise its normal native auto-merge path applies. Exactly what is deterministic vs. semantic

Deterministic, trusted checks

  • Trigger actor, event type, repository, fork status, PR state, draft state, base ref, and exact head/base SHAs.
  • Exact-head Review Agent approval and current risk assessment are present and bound to the same run.
  • Policy fingerprints, semantic fingerprints, context fingerprints, schema, decision, blockers, and evidence comment IDs match.
  • Risk is within the configured maximum; optional quality evidence is enforced only when configured.
  • Fresh postflight sees the same immutable binding before any SCM request; idempotency avoids duplicate native requests.

Non-deterministic semantic judgment

  • Does the change achieve its intended outcome, rather than merely pass CI?
  • Is its assessed scope and risk appropriate for unattended merging?
  • Does a human comment express “do not merge”, a hold, sequencing dependency, coordination need, or required follow-up?
  • Does the risk rationale and optional Review-quality signal support trusting this specific run?
  • Should the result be AUTHORIZE, DEFER, or ESCALATE when the evidence is ambiguous?
What this does not duplicate: Auto-Merge does not reimplement GitHub’s required-check evaluation, review-count rules, conversation-resolution rules, branch freshness, mergeability, or queue mechanics. It adds the semantic authority boundary around the questions GitHub cannot infer from SCM state alone, then hands the exact revision back to GitHub.
