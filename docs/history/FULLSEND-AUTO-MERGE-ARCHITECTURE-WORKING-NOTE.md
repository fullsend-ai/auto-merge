# Fullsend Auto-Merge Agent Architecture & Decision Model

Source: internal architecture working document
Captured: 2026-09-16
Status: Architecture direction agreed in discussion; exact gate inventory and implementation contracts remain to be finalized.

> **Core invariant:** A PR may merge only when the forge and Fullsend independently approve the same current change state, and that state is revalidated immediately before execution.

## 1. Executive summary

The Fullsend Auto-Merge capability should not be defined as an agent that simply enables a forge-native auto-merge switch. Its purpose is broader: it acts as Fullsend's final merge-authorization layer after repository-native governance and Fullsend's deterministic prerequisites have passed.

The forge and Fullsend answer different questions. The forge determines whether the PR satisfies repository-specific merge policy. Fullsend determines whether the complete evidence generated by the agentic SDLC is strong enough to authorize an unattended merge for the exact current SHA.

The implementation should preserve the existing execution pattern:

```text
pre-script -> LLM -> post-script
```

The pre-script performs inexpensive deterministic gating and can stop before an LLM call. The Review Agent performs the non-deterministic semantic code judgment. The Auto-Merge LLM validates that Review result for legibility and coherence before authorizing unattended execution. The post-script revalidates authoritative state and invokes the configured forge merge mechanism.

> **Decision principle:** Forge approval is necessary, but not sufficient, for Fullsend approval. Fullsend must never bypass repository governance, and repository governance must not substitute for Fullsend's final authorization.

## 2. What problem the Auto-Merge agent actually solves

The architectural question is not merely, “Can this PR be merged?” A forge can already answer much of that through branch protection, rulesets, required checks, approvals, conflict detection, merge queues, and related controls.

The Fullsend question is stronger:

> Given the complete context of this change and everything that occurred during the Fullsend workflow, should Fullsend authorize this exact change to merge without another human decision?

| Layer | Question answered | Primary responsibility |
| --- | --- | --- |
| Forge | Is this PR mergeable under this repository's configured rules? | Repository governance and integration mechanics |
| Fullsend pre-script | Are all objective Fullsend prerequisites true right now? | Deterministic eligibility filtering |
| Review Agent | Does the change satisfy its intent and meet correctness, security, and scope expectations? | Semantic review authority |
| Auto-Merge LLM | Is the Review Agent's exact-head result legible, coherent, and safe to use for unattended authorization? | Review-result validation and authorization |
| Fullsend post-script | Is the authorized state still current and safe to execute? | Deterministic revalidation and mutation |

## 3. Terminology and separation of concerns

| Term | Meaning | What it is not |
| --- | --- | --- |
| Forge mergeability | The forge reports that configured repository rules and merge constraints are satisfied for the current state. | Not Fullsend's final approval. |
| Forge auto-merge | A native mechanism that can execute a merge later when forge-defined conditions become true. | Not the Fullsend Auto-Merge Agent. |
| Fullsend merge authorization | A Fullsend decision that the exact current change is permitted to enter the merge path. | Not permission to bypass repository rules. |
| Auto-Merge pre-script | Cheap deterministic gate evaluation before any LLM call. | Not a semantic reviewer. |
| Auto-Merge LLM | Non-deterministic reasoning over the final evidence package. | Not the component that directly mutates source of truth. |
| Auto-Merge post-script | Deterministic revalidation and execution against the forge. | Not a second semantic review. |

> **Naming recommendation:** Use a gate such as `FORGE_MERGEABILITY=PASS` rather than checking whether the forge's auto-merge toggle is enabled. The former represents repository policy state; the latter is an execution instruction.

## 4. Proposed end-to-end architecture

```text
PR/MR evolves through the Fullsend workflow
        |
        v
Forge mergeability / repository policy = PASS
        |
        v
Fullsend Auto-Merge pre-script = PASS
        |
        v
Fullsend Auto-Merge semantic decision = APPROVE
        |
        v
Post-script revalidates exact current state
        |
        v
Configured forge mechanism executes merge
```

The ordering establishes a strict hierarchy:

- The forge's repository policy must be respected first. Fullsend never treats its own approval as a bypass.
- Fullsend's deterministic pre-script filters candidates that are objectively not ready.
- Only a fully eligible candidate reaches the LLM.
- The LLM can decline or escalate even when every deterministic check is green.
- The post-script checks that the world has not changed between authorization and execution.
- The final merge may use forge-native primitives such as a direct merge, queue, train, or native auto-merge mechanism, depending on repository policy.

## 5. Auto-Merge pre-script: deterministic eligibility

The pre-script should contain as many high-confidence deterministic gates as practical. A failed precondition should short-circuit before the LLM runs. This reduces cost and noise and prevents the model from reasoning about objectively ineligible candidates.

| Candidate gate | Typical result | Why it belongs before the LLM |
| --- | --- | --- |
| PR/MR is open | PASS / STOP | Closed, draft, or inactive changes cannot proceed. |
| Current HEAD SHA known | PASS / STOP | Authorization must bind to an exact code state. |
| Review Agent approved current SHA | PASS / STOP | Prevents merge before review and prevents stale approval. |
| Required CI checks passed | PASS / STOP | Objective pipeline state; no model judgment is needed. |
| Forge mergeability/rules passed | PASS / STOP | Preserves repository governance and branch protection. |
| Required Fullsend agents complete | PASS / STOP | Prevents final authorization while upstream work is unfinished. |
| No blocking agent/system failures | PASS / STOP | A known system failure is sufficient to withhold merge. |
| Reviewed SHA equals current SHA | PASS / STOP | Prevents approval of one state from authorizing another. |
| Required human approvals satisfied | PASS / STOP | Fullsend must not reinterpret a repository requirement. |
| No unresolved deterministic blockers | PASS / STOP | Examples: conflicts, holds, explicit blocks, or missing artifacts. |

> **Cost-control rule:** If the pre-script already knows the PR cannot be authorized, do not invoke the Auto-Merge LLM. A model call is reserved for a candidate genuinely eligible for semantic adjudication.

## 6. Auto-Merge LLM: the semantic gate

The Auto-Merge LLM receives a compact but complete evidence package describing the final candidate state and the Review Agent result. The Review Agent remains the authority for correctness, security, and intent satisfaction. Auto-Merge does not redo that review; it checks whether the Review result is legible, internally consistent, exact-head bound, and safe to use as unattended authorization. If the Review Agent's conclusion appears hallucinated, contradictory, or insufficiently supported, Auto-Merge escalates instead of authorizing.

Potential evidence inputs include:

- Issue/refinement intent and acceptance criteria, as context for validating the Review result.
- Final PR/MR diff and change summary, as context for checking that result's binding.
- Review Agent verdict, rationale, and structured findings as the semantic authority.
- Fix Agent history, including whether earlier findings were corrected.
- Code Agent execution context and relevant decisions.
- Test, security, quality, and CI summaries.
- Human review/comment state and remaining uncertainty.
- Signals about scope expansion, unusual behavior, risk, or conflicting evidence.
- Repository context and Fullsend policy relevant to unattended merges.

The semantic output should be structured and machine-consumable:

| Field | Example | Purpose |
| --- | --- | --- |
| `decision` | `APPROVE` / `REJECT` / `ESCALATE` | Explicit downstream control signal. |
| `reviewed_head_sha` | `abc123...` | Binds the judgment to an exact code state. |
| `reason_codes` | `OUT_OF_SCOPE_CHANGE` | Machine-readable explanation and analytics. |
| `summary` | One-paragraph rationale | Human auditability. |
| `uncertainties` | Partial-success path not validated | Makes residual risk visible. |
| `evidence_refs` | Review packet / checks / traces | Traceability to source evidence. |

## 7. Why Fullsend should not merely enable forge auto-merge early

The central concern is standing authorization. Enabling a forge-native auto-merge instruction before Fullsend reaches its own final decision means the forge may later merge as soon as its configured conditions become true. That makes forge conditions the effective final authority and creates races around revoking permission.

| Risk | Early forge auto-merge model | Fullsend final-authorization model |
| --- | --- | --- |
| Standing authorization | Merge permission exists while Fullsend is still evaluating. | No merge permission exists until Fullsend finishes. |
| Semantic context | Forge sees configured rules and checks. | Fullsend incorporates agent history, intent, scope, uncertainty, and cross-agent evidence. |
| Cancellation race | Fullsend may need to disable auto-merge before the forge executes. | Nothing needs to be revoked because authority is granted only at the end. |
| SHA integrity | A later state could become forge-eligible after earlier Fullsend activity. | Authorization is bound to an exact SHA and revalidated. |
| Portability | Behavior centers on a forge-specific feature. | Fullsend owns one policy contract and maps execution to supported forges. |
| Auditability | Why a merge happened may be spread across forge state changes. | One Fullsend authorization artifact explains the final decision. |

> **Architectural distinction:** Turning on forge auto-merge is an action. Deciding that a change is safe and appropriate for an unattended merge is a decision. Fullsend Auto-Merge should own the decision; the forge should own repository governance and merge mechanics.

## 8. Trigger strategy: event-driven, readiness-driven LLM invocation

Review Agent approval is an important trigger event, but it should not be the only trigger. The order in which CI, review, approvals, and forge state become green is not guaranteed. If Auto-Merge wakes only when review approval arrives, it can miss a later transition in which CI becomes the final missing prerequisite.

> **Recommended trigger rule:** Merge-relevant state changes wake Auto-Merge reconciliation. The LLM runs only when the pre-script detects that the current SHA has transitioned into a fully eligible candidate state.

| Event | Action | LLM call? |
| --- | --- | --- |
| Review Agent approves | Reconcile deterministic readiness. | Only if every prerequisite is now satisfied. |
| Required CI check changes | Reconcile deterministic readiness. | Only if every prerequisite is now satisfied. |
| New commit pushed | Invalidate prior candidate; reconcile the new SHA. | Usually no, until the new SHA becomes eligible. |
| Required approval/comment changes | Reconcile readiness. | Only on a fully eligible state. |
| Forge mergeability changes | Reconcile readiness. | Only on a fully eligible state. |
| Required Fullsend agent completes | Reconcile readiness. | Only on a fully eligible state. |
| Manual “Evaluate Auto-Merge” request | Run the same pre-script pathway. | Only if hard gates pass. |

## 9. Why Review approval alone is not a sufficient trigger

Consider two valid orderings:

| Timeline A | Timeline B |
| --- | --- |
| 10:00 PR created | 10:00 PR created |
| 10:03 Review Agent approves | 10:03 CI passes |
| 10:06 CI passes | 10:06 Review Agent approves |

If Review Agent approval is the sole trigger, Timeline A can fail operationally: the pre-script wakes at 10:03, sees CI pending, stops, and nothing necessarily wakes Auto-Merge when CI passes at 10:06. An event-driven reconciler avoids dependence on which prerequisite happens to complete last.

## 10. Idempotency, SHA binding, and state transitions

Auto-Merge should behave like a reconciler, not a one-shot webhook handler. Multiple events can arrive for the same state. The implementation should deduplicate by candidate identity so duplicate webhooks do not create duplicate LLM calls or duplicate mutations.

| State concept | Recommended behavior |
| --- | --- |
| Candidate identity | At minimum: repository + PR/MR + current HEAD SHA. Optionally include a relevant state/version fingerprint. |
| Already evaluated | Do not rerun the LLM for the same candidate state unless a relevant policy/evidence change invalidates the prior result. |
| New commit | Invalidate prior authorization and readiness for the old SHA. |
| Re-review | Review Agent must approve the new SHA if review approval is SHA-bound. |
| Reauthorization | A new eligible SHA receives a fresh Auto-Merge decision. |
| Execution revalidation | Post-script compares current authoritative state to the authorized candidate immediately before mutation. |

## 11. Concrete PR scenarios

### 11.1 Scenario A — Forge says yes, Fullsend says no

Issue: “Add retry behavior when the payments API returns HTTP 503.”

1. PR #427 is created at SHA A.
2. Unit, integration, and security checks pass.
3. Review Agent approves SHA A.
4. Forge mergeability is green.
5. Auto-Merge pre-script passes and invokes the LLM.
6. The LLM observes that retry behavior was added, but the final diff also changes retry count from 3 to 10 and timeout from 2 seconds to 30 seconds—a meaningful behavioral expansion beyond the requested scope.
7. Auto-Merge returns `REJECT` or `ESCALATE`.
8. Outcome: no merge, even though the forge considers the PR technically mergeable.

> **What this proves:** The Auto-Merge Agent is not redundant. It can evaluate intent, scope, and residual risk outside ordinary forge mergeability rules.

### 11.2 Scenario B — Review approved SHA A, Fix Agent creates SHA B

1. Review Agent approves SHA A.
2. Fix Agent later pushes SHA B.
3. A merge-relevant event wakes Auto-Merge.
4. Pre-script checks `reviewed_sha == current_sha`.
5. A does not equal B, so the pre-script stops immediately.
6. Review and other required checks must establish readiness for SHA B before Auto-Merge can evaluate it.

> **What this proves:** Approval for one code state must never authorize a different code state. The protection is deterministic and should not depend on LLM reasoning.

### 11.3 Scenario C — All hard gates pass, evidence is still insufficient

1. CI, security, repository policy, and Review Agent are green.
2. The history shows multiple Fix Agent iterations and an earlier Review Agent rejection.
3. The final Review Agent approval notes that a partial-success behavior could not be validated.
4. The candidate is technically mergeable.
5. Auto-Merge can still return `ESCALATE` because the evidence does not justify a fully unattended merge.

> **What this proves:** The meaningful question is not simply “Can it merge?” but “Is the evidence strong enough for Fullsend to authorize this without another human decision?”

### 11.4 Scenario D — Early forge auto-merge creates a cancellation race

| Time | Event |
| --- | --- |
| 10:00 | PR created. |
| 10:01 | Fullsend enables forge-native auto-merge before final Fullsend authorization. |
| 10:05 | CI passes. |
| 10:06 | Review Agent approves. |
| 10:06:02 | Forge sees its requirements satisfied and is free to execute the merge. |
| 10:06:03 | Fullsend discovers a semantic concern and attempts to disable auto-merge. |

The architecture has created a race between forge execution and Fullsend cancellation. The safer pattern is to avoid creating merge authority until the final Fullsend decision has already been made.

### 11.5 Scenario E — State changes after LLM approval but before execution

1. All gates pass for SHA C.
2. Auto-Merge LLM returns `APPROVE` for SHA C.
3. Before the post-script mutates the forge, someone pushes SHA D.
4. Post-script re-reads authoritative state.
5. `current_sha != approved_sha`, so execution aborts.

> **What this proves:** The post-script protects the final race window. The model does not need to solve concurrency; deterministic revalidation does.

## 12. Auto-Merge post-script: revalidate, then execute

The post-script should be deliberately small, deterministic, and privileged. The LLM's structured output is an authorization proposal, not a direct source-control mutation.

Immediately before execution, re-check authoritative forge state:

- PR/MR is still open and eligible.
- Current HEAD SHA still equals the SHA authorized by Auto-Merge.
- Forge mergeability and required checks still pass.
- No new block, hold, or review requirement has appeared.
- Required Fullsend preconditions remain true.
- The authorization has not expired or been superseded.

If any revalidation fails, abort the mutation. If all checks pass, invoke the repository's configured execution mechanism. Fullsend can remain forge-neutral at the policy layer while the post-script adapts to GitHub, GitLab, merge queues, merge trains, or other supported mechanisms.

## 13. Human trigger and override model

Humans should be able to request an Auto-Merge evaluation, but the normal manual trigger should enter the exact same pre-script → LLM → post-script path. A manual request must not silently bypass deterministic gates.

| Operation | Recommended semantics |
| --- | --- |
| Manual evaluate | Wake Auto-Merge reconciliation now. Hard gates still apply. |
| Manual retry | Re-run only when a prior transient/system failure warrants it; preserve the audit trail. |
| Administrative override | If ever supported, define it as a separate privileged operation with explicit reason, authorization, and audit logging. |
| Emergency direct merge | Treat it as outside normal Auto-Merge semantics rather than overloading the agent's approval contract. |

## 14. Decision matrix

| Forge | Fullsend pre-script | LLM | Post-script | Result |
| --- | --- | --- | --- | --- |
| FAIL | Not eligible | Not run | Not run | No merge |
| PASS | FAIL | Not run | Not run | No merge |
| PASS | PASS | REJECT | Not run | No merge |
| PASS | PASS | ESCALATE | Not run | Human decision required |
| PASS | PASS | APPROVE | Revalidation FAIL | No merge; reevaluate current state |
| PASS | PASS | APPROVE | Revalidation PASS | Execute configured merge mechanism |

## 15. Responsibility matrix

| Concern | Forge | Pre-script | LLM | Post-script |
| --- | --- | --- | --- | --- |
| Repository-specific branch/merge rules | Owner | Consumes result | Context only | Rechecks |
| Required CI state | Source of truth / enforcement | Checks | Uses summary | Rechecks |
| Review Agent approval | May receive status | Checks exact SHA | Uses rationale | Rechecks as needed |
| Intent/scope reasoning | No | No | Owner | No |
| Cross-agent evidence synthesis | No | No | Owner | No |
| Exact-SHA authorization | Supports state | Verifies | Binds decision | Enforces |
| Final source-control mutation | Executes | No | No | Invokes forge |

## 16. ADR-ready decision language

> Fullsend Auto-Merge will provide an additional merge-authorization layer above repository-native merge policy. A change must satisfy both the forge's mergeability requirements and Fullsend's deterministic and semantic authorization requirements before the Fullsend post-script may execute the configured merge mechanism.

Recommended ADR statements:

- Forge approval is necessary, but not sufficient, for Fullsend approval.
- Fullsend Auto-Merge owns the merge-authorization decision; the forge owns repository governance and merge execution mechanics.
- Auto-Merge is event-driven, but LLM invocation is readiness-driven.
- Merge-relevant events cause deterministic reconciliation; the model runs only for a fully eligible current candidate.
- Every authorization is bound to an exact current SHA.
- A new commit invalidates prior merge authorization unless explicitly proven equivalent by policy; default behavior is re-evaluation.
- The post-script must revalidate authoritative state immediately before mutation.
- Normal human-triggered evaluation does not bypass hard deterministic gates.

## 17. Audit and observability requirements

Each attempted authorization should record both the state that caused evaluation and the evidence used to decide.

| Audit field | Why capture it |
| --- | --- |
| Repository + PR/MR ID | Stable change identity. |
| Candidate SHA | Exact state considered. |
| Triggering event | Explains why reconciliation occurred. |
| Pre-script gate results | Shows why the LLM did or did not run. |
| Forge mergeability snapshot | Records repository-policy state at decision time. |
| Review Agent result/reference | Connects final authorization to review evidence. |
| LLM decision + reason codes | Explains semantic outcome. |
| Post-script revalidation | Shows whether authorized state was still current. |
| Execution mechanism/result | Documents queue/train/direct merge action and outcome. |
| Correlation/trace ID | Allows reconstruction across Fullsend services and agents. |

## 18. Explicit anti-goals

- Do not rebuild every forge's branch-protection or merge-policy engine inside Fullsend.
- Do not define Auto-Merge as merely an AI wrapper around a GitHub/GitLab auto-merge toggle.
- Do not pay for LLM reasoning when deterministic gates already prove the PR ineligible.
- Do not let the LLM directly mutate the forge or hold privileged merge credentials when a deterministic post-script can execute the action.
- Do not allow an approval for SHA A to authorize SHA B.
- Do not make Review Agent approval the sole wake-up event for autonomous merge readiness.

| What state fingerprint drives idempotency? | Prevents duplicate model calls and duplicate actions. |

## 20. One-page team summary

Fullsend Auto-Merge should be the final Fullsend authorization layer, not merely an automation that turns on a forge-native auto-merge feature. Repository rules remain mandatory; Fullsend adds deterministic and semantic requirements on top.

| Step | Rule |
| --- | --- |
| 1. Reconcile | Any merge-relevant state change wakes the pre-script. |
| 2. Deterministic gate | If any hard prerequisite fails, stop without an LLM call. |
| 3. Semantic gate | If all hard gates pass, ask whether Fullsend should authorize unattended merge for this exact SHA. |
| 4. Revalidate | Immediately before mutation, verify the authorized state is still current. |
| 5. Execute | Use the repository's configured forge-native merge mechanism. |

> **Memorable phrasing:** Forge says, “This is mergeable under repository policy.” Fullsend says, “Given everything we know, this exact change is authorized for unattended merge.” Both must be true.

> **Trigger phrasing:** Auto-Merge is event-driven, but LLM invocation is readiness-driven.
